# 开发进展记录

这份文档记一些项目推进过程中的工作笔记。

## 总起

这次比赛的评测方式已经基本摸清了。仓库根目录里必须有 `Makefile`，评测时会直接执行 `make all`，最后需要产出 `kernel-rv` 和 `kernel-la`。QEMU 启动之后，官方测试镜像会被挂载进来，内核需要自己去扫描测试脚本并按顺序运行。也就是说，最终提交时到底跑哪些测试，不是简单由一条 QEMU 命令决定的，而是由烧进内核里的用户态测试调度逻辑决定的。现在已经明确，提交链主要看 `run_submit()`，而不是 `run_all()`。

开发环境这边也有一套固定约定，后面尽量不要再变。宿主机仓库目录是 `D:\S-OS`，容器名是 `sos3_d`，容器里真正使用的仓库根目录是 `/workspace`。之前一度还混用过 `/workspace/S-OS` 这条旧路径，后来确认那是历史残留，不应该继续拿来做主工作区。后续如果再需要看容器里的代码或者跑编译、测试，一律默认 `/workspace`。

测试方式现在也已经收敛。RISC-V 走 `sh /workspace/tools/run_qemu_rv_clean.sh /workspace/sdcard-rv.img`，LoongArch 走 `sh /workspace/tools/run_qemu_la_clean.sh /workspace/sdcard-la.img`。这两个脚本会先把镜像复制到 `/tmp` 下，再做一次 `e2fsck`，最后拿临时副本启动 QEMU，所以刚开始一小段时间没有输出通常是正常现象。这个流程比直接挂载原始镜像稳得多，后面所有回归测试都尽量按照这个方式来。

还有几件事已经确认过，后面就不再反复试错了。第一，`libctest` 只有 musl，没有 glibc；第二，`libcbench` 不是单纯看能不能跑通，还和性能得分有关；第三，LTP 现在不适合全量直接硬跑，必须用 curated case 的方式逐步扩展。

## 第一阶段：先把评测链和代码入口看明白

一开始最主要的工作不是写代码，而是先把整个项目到底怎么被比赛平台调用搞清楚。那时候最困惑的问题其实很朴素，就是“我改了哪里，评测时到底会不会生效”。后面花了一些时间读 `Makefile`、读 `user/riscv/user.c` 和 `user/loongarch/user.c`，把测试入口逻辑顺了一遍，才慢慢确认真正决定提交行为的是 `run_submit()` 这一层，而不是平时手工输入的 QEMU 命令。

这个阶段的收获很重要，因为它直接影响后面的开发方法。以前如果测试结果不对，很容易第一反应去怀疑 QEMU 参数或者怀疑脚本没有跑到，但后面已经比较清楚了：如果要改变提交版本到底跑哪些测试组，关键是改用户态测试组织逻辑，而不是盯着外部启动命令打转。

## 第二阶段：把 Docker、WSL、宿主机路径关系理顺

这部分虽然看起来不像“内核开发”，但实际上占了不少时间，而且不解决的话后面很容易出现假的结论。前期有一段时间，容器里的内容、D 盘仓库、C 盘的旧副本是混在一起的。用户本地测试能跑出来的东西，有时不一定和 Git 仓库里将要提交的内容完全一致。我这边后面是靠反复核对容器路径、宿主机目录、`docker cp` 的来源和目标，才慢慢把这件事理顺。

其中一个比较关键的结论是：容器里真正应当工作的路径是 `/workspace`，不是 `/workspace/S-OS`。这个问题后来反复影响判断，因为旧路径里残留过老文件、老镜像、老构建结果，如果一不小心又回到那边去测，得到的现象就会和当前代码不一致。后面我们干脆把 `/workspace` 当成唯一标准路径来用，这样至少上下文不会再漂来漂去。

Docker 和 WSL 本身也出过一次比较重的故障，后面还牵扯到 Docker Desktop 起不来、`docker ps -a` 卡死、Docker 数据目录膨胀、WSL 里的 ext4 文件系统检查这些问题。这一段本质上不是在做功能开发，而是在抢救开发环境。好在最后没有选择彻底推倒重建，而是尽量保住了现有容器和工作区，把环境恢复到了可以继续编译和测试的状态。

## 第三阶段：定位“镜像被写脏”这个大坑

项目进入实测之后，很快就发现一个现象：同样的代码、同样的命令，这次能跑到后面，下次却可能在前面就 panic，尤其是文件系统相关的报错非常随机。最开始会本能地去怀疑内核改坏了，后来通过对 `sdcard-rv.img` 和 `sdcard-la.img` 做 `e2fsck -fn` 检查，才逐渐确认一个更底层的问题：测试镜像本身会在运行过程中被改写，而且改写之后不一定还是一致的 ext4 状态。

那段时间看到过很多典型现象，比如 inode 异常、目录损坏、filetype 错误、free inode 和 free block 计数不一致。到这个阶段基本已经能判断，很多 ext4 panic 不是当前改动直接造成的，而是之前某次测试已经把镜像污染了。这个问题如果不先解决，后面所有测试结论都会被拖歪。

所以再往后，我们把“干净镜像测试”变成了默认流程。也就是每次测试前都复制一份临时镜像，在副本上做 fsck，然后只拿副本给 QEMU 用。这个改动听起来很工程化，但实际上非常值，因为它第一次把“镜像状态问题”和“代码问题”分离开了。后面一条链如果又炸了，至少可以先排除是不是镜像早就坏了。

## 第四阶段：先把 basic、busybox、libc 这些主链修平

真正开始追分之后，最开始的重点不是 LTP，而是把已有主链测试先跑顺。那时候 basic、busybox、libc_all、libctest、libcbench 都有各自的问题，有些是功能没实现完整，有些是输出格式对不上，还有些是跑到中间会卡住。busybox 这条线尤其折腾，曾经出现过提交测评卡在 `busybox-glibc` 的情况，本地和平台表现还不完全一样。

那一段做过很多排查。比如有段时间怀疑是 `date`，后来又更像是 `cal` 或者终端相关的 `ioctl` 行为。还有一些问题不是测试本身挂了，而是输出格式不被评测器接受，结果看起来像“没得分”。后面随着这部分一点一点修平，basic 和 busybox 的分数开始明显回升，至少主链不再轻易被前面的基础测试拖垮。

libc 这边则主要是两件事。第一是把概念理顺，明确 `libctest` 没有 glibc 测试点，不要再把不存在的目标当成问题追。第二是逐步接受 `libcbench` 和普通功能测试不是一回事，它能跑完不等于得分就高，因为性能本身也参与了评判。这一点对后面的优化方向影响很大，相当于先把“兼容性问题”和“性能问题”分开看了。

## 第五阶段：LTP 接入、格式对齐和 curated case 机制

LTP 是中后期的核心战场，但一开始并不是所有问题都出在内核能力上。很大一部分时间其实花在让输出格式被评测器识别。比如最早输出的测试组名字带了架构后缀，像 `ltp-musl-rv` 这种形式，本地看没有问题，但平台并不一定按这个名字来认分。后面改成更贴近评测器预期的 `ltp-musl`、`ltp-glibc` 这一类分组名之后，情况才开始变好。

还有一个典型问题是 LTP 内部明明出现了不少 `TPASS`，但最后的 `Summary` 里却全是 0。这个问题后来确认过，并不是“没跑到”，而是运行包装方式、summary 收集方式和 LTP 预期之间没有完全对齐。把这一层理顺以后，summary 才真正开始反映 case 的执行结果，评测器才有可能给分。

也是从这里开始，我们彻底放弃了“全量 LTP 直接跑”的思路。当前内核完成度下，这种做法副作用太大，很容易为了多试几个点把整条链直接炸掉。后面改成 curated case 机制，在 `user/riscv/user.c` 和 `user/loongarch/user.c` 里维护相对保守的 case 列表，优先保留那些已经稳定、不会拖垮整条链而且确实能换来分数的 case。这个策略虽然保守，但在比赛环境里是合理的。

## 第六阶段：用 probe 脚本替代手工瞎试

当 LTP case 数量一多，靠手工一点点改数组、编译、重跑、看结果，效率很快就不够了。后面就专门加了一套探测脚本，也就是 `tools/probe_ltp_common.sh`、`tools/probe_ltp_rv.sh` 和 `tools/probe_ltp_la.sh`。它们的作用不是直接用于提交，而是先帮忙回答一个更基础的问题：到底哪些 case 目前能启动、能收尾、不会把系统立刻炸死。

这一套脚本后来会输出 `summary.tsv` 和 `stable_cases.txt`，把每个 case 的状态、退出码以及 summary 里的统计信息集中起来。这样再去挑 curated 列表时，至少不是完全靠感觉，而是有一份本地探测结果作为依据。后面还顺手把它改成了固定目录覆盖的形式，避免时间戳目录堆积太多、反而干扰判断。

## 第七阶段：平台测评分数开始回升，但回退也变成常态

随着 basic、busybox、libc 和 LTP 输出问题逐步被修掉，平台分数有过几轮比较明显的回升。尤其是 `ltp-musl-rv`，一度成为四个 LTP 组合里相对最稳定、最有收益的一组。与此同时，也能看出来 `ltp-glibc-la` 长期偏弱，而 `ltp-musl-la` 的分数波动比较大。

但这个阶段也伴随着大量回退。原因很简单：一旦进入线程、信号、LTP 深水区，某次改动即使在局部看起来是有效的，也可能把原本已经修好的主链拖下来。后面多次出现“本地觉得好了，提交反而更差”的情况，也多次出现“一个问题修了，另一个更大的问题出来了”的情况。所以开发策略也逐渐从“大胆尝试”转成了“高分版本为基线，小步前进”。后期的很多工作，其实都是先回到上一版高分代码，再带着新的理解重新试。

## 第八阶段：线程、futex、signal、cancel 这条底层链开始暴露出来

真正最难的一段，是当 `pthread_cancel_points` 和 LTP 随机 panic 逐渐变成主要问题的时候。到这个阶段，已经很难再把问题简单归因到某个 case 没兼容，因为现象本身就带着明显的随机性：这次在这个点炸，下次可能在另一个点炸，而且 RISC-V 和 LoongArch 两边都可能出现。

围绕这个问题，后面陆续排查过 `tgkill`、`tkill`、`futex wait / wake`、`rt_sigreturn`、signal frame、`usersigreturn`、`SIGTRAMP`、`clone_thread`、调度切换和 `trapframe->kernel_sp` 这些路径。结论没有一次性完全收敛，但有一些方向越来越可疑。比如 `pthread_cancel_points` 这种 case 的失败，很可能不是 case 自己有多特殊，而是它刚好把线程取消、信号送达、futex 中断返回、用户态恢复这些路径全踩了一遍，因此把底层稳定性问题放大了。

后期最值得记住的认识是：随机 panic 往往不是“随机”，而是线程底层状态在某个条件下已经被写坏了，只不过真正炸开的时间点不固定。也正因为这样，后面如果再出现这一类现象，优先排查的路径就比较明确了，还是从 `clone_thread`、线程 kernel stack、`kernel_sp`、调度切换和 futex / signal 交汇处入手。
