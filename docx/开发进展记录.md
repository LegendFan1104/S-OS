# 开发进展记录

开发过程中的笔记，记录一些关键决策和踩过的坑。

---

## 总起

先搞清楚评测怎么跑的。仓库根目录必须有 `Makefile`，评测跑 `make all`，产出 `kernel-rv` 和 `kernel-la`。内核启动后自己去挂载的镜像里扫描测试脚本、按序执行。这意味着提交时跑哪些测试，不是靠 QEMU 启动参数控制的，而是由内核里的用户态测试调度逻辑决定——关键路径是 `run_submit()`，`run_all()` 只是本地调试用的。

环境这边，宿主机 `D:\S-OS`，容器 `sos`，工作路径统一用 `/workspace`（旧路径 `/workspace/S-OS` 早就废了，但曾经因为路径混用浪费了不少排查时间）。测试流程也固定了：先把镜像拷到 `/tmp`，`e2fsck` 检查一遍，再拿副本启 QEMU。这个流程比直接挂原始镜像稳太多——后面会反复提到镜像被写脏的问题。

几件事确认后就不再纠结了：`libctest` 只有 musl 没有 glibc（别在不存在的东西上浪费时间）；`libcbench` 跟性能挂钩，不是跑通就行；LTP 不能全量硬跑，必须 curated case 逐步来。

## 学习与方案设计

项目开始没急着写代码。先啃了两本架构手册——RISC-V 特权架构（S 态 CSR、`sret`/`mret`、Sv39 页表、TLB 重填）和 LoongArch（`ertn`、四级页表、DMW 直映窗口）。同时把 xv6-riscv 源码过了一遍。两边的差异比预想的大：RV 三级页表、LA 四级页表；RV 用 `sscratch` 传 trapframe、LA 用 `CSR_SAVE0`；RV 的定时器走 SBI、LA 走 MMC。如果不先吃透这些差异，后面 HAL 层的抽象边界根本画不对。

选 xv6-riscv 当 baseline 没什么争议。关键决定是定下 HAL/HSAI 双层架构——跟硬件绑定的放 `hal/`（双架构各自实现），差异封装放 `hsai/`（统一的接口层），上层 `kernel/` 完全不感知架构差异。这个设计后面证明是对的：一次改动只需在一处生效，不用在 `#ifdef RISCV` 和 `#else` 之间来回跳。

Docker 环境搭的时候出过一次大故障——Docker Desktop 启动不了、`docker ps -a` 卡死、WSL 的 ext4 需要修复。那几天基本没写代码，全在抢救环境。最后没选择推倒重来，把现有容器和 workspace 保住了。代价是花了不少时间，但保住了已经配好的交叉编译工具链。

## 第一次完整提交

提交信息 "SOS operating system — full project snapshot"。80+ 个文件一口气上去：lwext4 完整移植、VirtIO 块设备驱动、PCI 扫描、Buddy + SLAB 内存分配、进程管理、调度器、trap 处理。选 lwext4 而不是从零写 ext4 驱动，这个决定很关键——ext4 规范太复杂，手写一个正确且稳定的实现代价太大，lwext4 是成熟的嵌入式 ext4 库，适配块设备接口就能用。后面的事实证明 lwext4 本身确实稳定，出问题的都是我们自己的 VFS 层和块设备驱动。

构建流程是：编译内核 → 交叉编译用户态程序 → 把编译好的 initcode 二进制嵌进内核镜像。`initcode-rv` 和 `initcode-la` 从 10KB/14KB 起步，随用户态程序增长一路膨胀，每一步背后都是新加的系统调用或测试逻辑。

## busybox 兼容和 LoongArch 适配

提交最密集的时段，一天十几笔，全围着 busybox 和 LA 适配。

### busybox 这条路

busybox 是后面所有测试的基础，它跑不通 LTP 就不用想了。思路是先让 busybox 的基本命令能工作——ps、kill、shell，然后逐步修边界情况。

第一关是 `busybox ps`。busybox 读的是 `/proc/[pid]/stat`，我们一开始的 procfs 实现很粗糙，很多字段是硬填的。`tty_nr` 填了 -1，busybox 看到这个值直接不显示该进程。改成 0 就好了。但紧接着又发现 kill 不生效——信号发送路径没有完整走通：`sys_kill` → `proc_kill` → 设置 `sig_pending` → 目标进程被唤醒。中间有几环是空的，补上之后才行。后面又修了一版，说明初版的理解还不够深——procfs 虽然看起来就是填几个字段，但 busybox 对字段格式的容忍度很低，每个字段都要跟 Linux 的行为对齐。

### shebang 和测试自动扫描

shebang 机制的思路很简单：`exec()` 加载文件时先读前几个字节，如果匹配 `#!` 就解析解释器路径，转而加载解释器，把脚本路径作为 argv[1]。集中在 `kernel/proc/exec.c` 里，83 行。这个功能虽然小，但 LTP 里大量 case 是 shell 脚本，全靠它才能跑。

自动扫描测试脚本也是类似思路——让 init 进程遍历根目录找测试可执行文件，而不是硬编码路径。这样加新测试不用改 init 代码。但紧接着就发现一个问题：直接 exec 可执行文件的话，shebang 不会被触发——因为脚本本身不是 ELF，exec 会失败。必须通过 shell 来执行：`/bin/sh ./test.sh`。所以 `492f821` 又修了一版，让测试执行走 shell 路径。

### LoongArch 这边的坑

LA 适配的问题一个接一个，但回头看不外乎几类：

一是编译链路问题。LA 的工具链自带 libc，但我们 Makefile 里又链了一次，产生隐式冲突。解决方式是在 LA 编译路径里去掉重复的 libc 链接。

二是路径问题。`disk-la.img` 路径、`init-loongarch.c` 里的硬编码路径都不对，导致 QEMU 启动后不是找不到磁盘就是找不到 init。这类问题排查起来很费时间——现象是"系统没起来"，但根因可能是什么都没有、也可能是某个路径少了 `/`。

三是系统调用差异。`sys_statx` 在 LA 端权限检查失败，追下去发现是 LA 的 trapframe 里系统调用参数的位置跟 RV 不一样，`hsai_get_arg()` 取参数时取歪了。这说明 HAL 层的抽象还不够干净——上层 syscall handler 不应该感知参数寄存器差异。

解决完这一批，两边架构基本能对等跑通 basic 和 busybox。

cyclictest 也试了一下，但发现时钟子系统精度不够——`clock_gettime` 的精度是 tick 级别（大概 10ms），cyclictest 需要微秒级。这个问题根子在 RISC-V 的 `set_next_timeout()` 时机和 tick 粒度上，当时判断不是优先事项，先搁置了。

## LTP 接入：基础设施先补齐

开始搞 LTP 的时候，很快就意识到一个问题：LTP 不是一个测试套件那么简单，它对系统调用的覆盖非常广。跑 LTP 之前，epoll、futex、signal 这三条腿必须基本齐全，否则连 case 都启动不了。

先补 epoll。LTP 里 `epoll_create1`、`epoll_ctl`、`epoll_wait`、`epoll_pwait` 这四个调用几乎所有涉及 I/O 的 case 都在用。从零写了 `kernel/fs/epoll.c`，304 行——核心是一个红黑树（存注册的 fd）+ 一个就绪链表（存触发事件）。epoll 的难点不在数据结构，而在跟 VFS 的集成：每次 `vfs_read`/`vfs_write` 返回时要检查是否有 epoll 在监听这个 fd，有的话要往就绪链表里塞事件。这个"触发点"散落在 VFS 各条路径上，容易漏。

futex 也要大改。busybox 阶段 futex 只有框架——`futex_wait` 和 `futex_wake` 只处理了最基本的"睡眠-唤醒"而不涉及超时和 requeue。glibc 的 pthread 对 futex 的依赖远比预想的重：pthread_mutex 的竞争路径走 futex、pthread_cond 的 wait/signal 走 futex、甚至 `pthread_join` 底层也是 futex。扩展到 78+ 行，把 `futex_wait` 的超时分支（`t_TIMING` 状态 + `awakeTime` 字段）、`futex_wake` 的批量唤醒、`futex_requeue` 的跨地址迁移都补上了。关键是 `futex_wait` 里的锁交接：先锁进程再放外部锁，否则存在"wake 先于 wait"的 lost wakeup 窗口。

signal 也要补。实时信号（`SIGRTMIN` ~ `SIGRTMAX`）、`sigaction` 的完整字段（`sa_mask`、`sa_flags`、`sa_restorer`）、`rt_sigreturn` 的用户态 trampoline——这些在 busybox 阶段基本没用上，但 LTP 的 signal 测试组全覆盖了。signal 框架扩展的核心难点是信号注入时机：必须在目标线程返回用户态的瞬间（`usertrapret` 之前）检查 `sig_pending` 并构造 signal frame 压栈。这个时机如果选在别处——比如调度器里——就会跟线程的 kernel stack 状态冲突。

系统调用号也加了 30 个。LTP 的 syscalls 测试组会遍历 `/sys/kernel/debug/` 下面暴露的系统调用列表，少一个调用号就直接跳过整组测试。

### panic 和回退

LTP 跑起来之后 panic 密度很高。有一个比较典型的：ext4 路径上的 panic 卡死。现象是某个 case 跑到一半整个系统停住，没有任何输出。排查方向一开始放在调度器——怀疑是死锁。但加了调度器状态 dump 后发现 CPU 在 idle 循环里，所有进程都在 SLEEPING，不像是死锁。

回头看文件系统。`fc43490` 试探性地改了 `vfs_ext4_ext.c`、`vfs/file.c`、`sysfile.c`——调整了 ext4 的 extent 操作缓存策略和 VFS 层的文件引用计数。commit message 直接写"若未修复回退到两次提交前"，说明当时对根因没把握。后来确实回退了（`d3bdea2`）。

这种"试一下、不行就退"的模式贯穿整个开发过程。因为很多问题不是单点 bug——ext4 VFS、块设备 buf 管理、调度时机、内存分配这几层之间的交互才触发。单独看每层逻辑都没问题，合在一起就有边界条件覆盖不到。

### 架构大改

`c932282` 是一次集中的架构调整。之前代码组织是比较扁平的——syscall 实现都在一个大文件里，调度和信号处理混在进程管理里。随着 LTP 的推进，这种组织方式越来越难维护。

把调度独立成 `syssched.c`（306 行）。`clone`、`clone_thread`、`sched_yield`、`setaffinity` 这些调用之前散落在 `sysproc.c` 里，但它们的逻辑跟进程创建的关联度不大，反而跟调度器（`scheduler`、`cpu_t`、`thread_t`）紧密相关。独立出来之后，调度相关修改的影响面更可控。

把信号独立成 `syssig.c`（55 行）。`tgkill`、`tkill`、`rt_sigaction`、`rt_sigreturn`——信号发送和处理是一个相对闭环的逻辑，独立出来是合理的。

`exec.c` 大改（+211 行），主要是支持动态链接器。之前 exec 只处理静态链接的 ELF——直接加载 segment、设 entry point 就行。但 glibc 的 LTP binary 是动态链接的，exec 之后要先加载 `ld.so`（动态链接器），然后 `ld.so` 再加载 `libc.so` 和其他依赖。这要求 exec 构造 aux vector——`AT_PHDR`、`AT_ENTRY`、`AT_BASE`、`AT_PAGESZ` 等等——放在栈上，让 `ld.so` 的用户态代码能读到。aux vector 的字段没给全的时候，`ld.so` 会直接 `SIGKILL` 自己，错误信息什么都没有，排查方向很难找。

同批还加了 `kernel/fs/procfs.c`（694 行）。之前 procfs 是散落在各处用 `if (strcmp(path, "/proc/..."))` 硬判断的，完全不可维护。/proc 下面几十个文件，每个的格式都不同——`/proc/[pid]/stat` 是一行空格分隔的数字、`/proc/mounts` 是经典的 mount 格式、`/proc/cpuinfo` 又是另一种格式。集中到 procfs.c 里统一管理，用注册机制（路径匹配 → 回调函数 → 生成内容），后面再加新文件就简单多了。

内存对齐和 sleep 卡死也是这一批修的。内存对齐的问题在于 `sbrk` 返回的地址没按架构要求对齐——RV 上 glibc malloc 要求 16 字节、LA 上更严——导致 `malloc` 返回的指针实际不可用。改动在 `sysmem.c`，`sbrk()` 返回前做一个 round-up。sleep 卡死则是 `sys_nanosleep` 的返回值处理有误——`tick` 计数溢出导致的边界情况。

## HAL 层正式抽离

`fd19fd4` 是最大的一次重构。之前 RV 和 LA 的代码混在 `kernel/trap/`、`kernel/proc/`、`kernel/mem/` 里，靠 `#ifdef RISCV` / `#else` 区分。每次改一个架构的细节，都可能误伤另一个——比如改 RV 的 trap 入口时动了共用代码，LA 端编不过。

把这层拆开的思路是：凡是直接操作硬件寄存器、跟指令集绑定的代码，放到 `hal/riscv/` 和 `hal/loongarch/`；凡是封装硬件差异、对外提供统一接口的，放到 `hsai/`；`kernel/` 只保留架构无关的逻辑。

具体动作：
- `kernel/trap/kernelvec.S` → `hal/riscv/kernelvec.S` 和 `hal/loongarch/kernelvec.S`（RV 和 LA 的中断向量完全不同）
- `kernel/trap/trampoline.S` → `hal/riscv/trampoline.S` 和 `hal/loongarch/trampoline.S`（用户态↔内核态切换的汇编蹦床）
- `kernel/proc/swtch.S` → `hal/riscv/switch.S` 和 `hal/loongarch/swtch.S`（上下文切换的寄存器保存/恢复）
- 新建 `hal/loongarch/tlbrefill.S`：LA 的 TLB 是软件重填的，缺页时硬件跳到 `tlbrefill` 入口，由软件遍历页表装载 TLB 项。RV 这边 TLB 是硬件管理的（`sfence.vma`），所以不需要这个文件。

`hsai/` 层放共享的体系结构接口代码：`hsai_trap.c`（931 行，是最大的一个文件，因为 trap 分发逻辑、系统调用路由、中断处理主循环都在这里）、`hsai_mem.c`、`hsai/plic.c`、`hsai/print.c`。

头文件也按这个层次重组了。之前 `include/` 是平铺的——`asm.h`、`defs.h`、几十个 ext4 头文件全部堆在一起。改成了：
- `include/hal/riscv/riscv.h`（390 行）和 `include/hal/loongarch/loongarch.h`（437 行）：各自的寄存器定义和 CSR 操作宏
- `include/hsai/`：HSAI 层接口头文件
- `include/kernel/fs/`：ext4 头文件从平铺改成放在 `fs/` 子目录，ext4.h 从 609 行扩展到了 1218 行

这次重构做完，改 RV 的 trap 处理不会碰 LA 的代码，反过来也是。开发效率提升很大——之前一个改动要确保两边的 `#ifdef` 分支都覆盖到，现在在 `hal/` 下各改各的。

## LTP 测试清单和 metadata

提交了 `ltp-info/`，74 个文件、28000+ 行。这个不是 LTP 源码（源码在编译时从外部拉），而是元数据和运行配置：`metadata/ltp.json`（20340 行，case 粒度的依赖关系、超时、行为描述）、`runtest/` 下 70 个测试组、`testcase_binaries.txt`（2842 行，全部 case 的二进制列表）。

引入这套 metadata 的思路是：curated case 不能靠感觉挑。要能回答"这个 case 需要哪些系统调用、预计跑多久、有没有已知的不稳定？" 对着 JSON 逐个过，把依赖未实现功能的先排除，把已知会卡死的先注释，剩下那些能启动、能收尾、不炸的才进列表。这个过程不靠 metadata 根本没法做——你不可能手工记住 20000 多行 case 信息。

## 文件系统适配 iozone

iozone 是一个文件系统 benchmark：顺序读写、随机读写、跨步读写、mmap I/O，各种模式轮一遍。一开始跑就 panic，而且每次 panic 的位置还不太一样。这跟之前 busybox 的场景完全不同——busybox 对文件系统的压力很小（读写几个字节、列个目录），很多边界条件根本碰不到。

### 块设备层的 panic

最早的一个 panic 在 `kernel/fs/blockdev.c`。iozone 做随机读写的时候，buf 的引用计数被减到了负数。追下去发现逻辑是这样的：`bget()` 在 buf cache 里找一个块，如果块正在被其他进程使用（`B_BUSY`），调用者应该 `sleep_on_chan` 等它释放。但有一个路径里 `brelse()` 唤醒等待者之后没有正确设置 `B_VALID` 标志，导致被唤醒的进程读到了未初始化的数据——然后它又调了一次 `brelse()`，引用计数就成负的了。

修复集中在 `blockdev.c` 的 32 行调整——主要是 `bget`/`bread`/`brelse` 之间的状态转换。块设备这层看起来简单（就是读块写块），但 buf 的生命周期管理有几个容易出错的地方：脏块的写回时机、等待队列的唤醒条件、B_VALID 和 B_DIRTY 标志的转换。

### 去掉 init_code 头文件

删了两个巨大的头文件——`la_init_code.h` 和 `rv_init_code.h`，加起来 5991 行。init_code 是编译好的用户态 init 程序，以前直接以 C 数组形式嵌在头文件里。这样做有两个问题：一是每次改用户态代码都要重新编译整个内核（因为头文件变了）；二是 5991 行的头文件 IDE 打开都费劲。

改成从外部二进制文件加载：内核镜像里留一个占位 section，构建脚本在链接之后把 initcode 二进制注入进去。这样改用户态程序只需要重新注入，不用重新编译内核。

### 热路径优化

iozone 能跑了之后性能是下一个问题。几个优化是逐步加上的：

第一个是 `vfs_ext4_read/write` 去掉每次 `kalloc/kfree`。原来每次读写 syscall 进来都分配一页（4096 字节）、用完释放。这对 `putc`/`getc` 这种高频小 I/O 来说是巨大的浪费——每次写一字节都要分配 4KB。改成固定 512 字节栈缓冲。选 512 而不是更大，是因为要平衡"覆盖大部分小块 I/O"和"不爆栈"——VFS 调用链已经比较深了，再加大的栈缓冲风险很高。这个优化对 iozone 的小块随机读写提升明显。

第二个是把 `mtime/ctime` 更新推迟到 `close()`。原来的逻辑是每次写操作都更新 inode 的时间戳——这要求每次写都启动一个 ext4 事务来修改 inode。但大多数短进程是打开文件、写几行、关闭——中间的 mtime 改了也白改，最后一次才重要。改成写路径只设 `f_time_dirty` 标记，`fileclose()` 再统一回写。对 LTP 里面的短进程 case 改善很大。

第三个是 `ext4_fwrite()` 的 fast path。lwext4 默认不管覆盖还是扩文件都启动事务，但纯覆盖已有数据块不需要——不会改超级块、位图、extent tree。加了一个判断：计算本次写入是否完全在 `file_size` 范围内，是的话跳过 `ext4_trans_start/stop`。这个优化的边界条件是"文件大小正好在块边界上"的情况——如果写入从块边界开始但长度为零，要小心不要误判。

### 链表防护

有一个随机 panic 是 `list.c:250 is_interior(elem)`。意思是链表遍历到某个节点，发现它的 `prev->next != this` 或 `next->prev != this`——节点已经被摘下但还当成在链上的。

排查过程很痛苦，因为不是每次都出。最后定位到 buddy 分配器：一个物理页被释放回 buddy 之后，它的 list elem 没清干净，又被其他路径（SLAB 分配器）误插入到另一个链表。加了三层检查：`list_insert()` 前确认节点不在任何链上、`list_remove()` 后清空 `prev/next`、buddy 合并前不仅检查元数据空闲还要确认 elem 确实在空闲链表里。

### probe 脚本

手工维护 curated case 列表效率太低了——改 `user.c` 里 case 数组 → 编译 → QEMU 跑 → 看哪些挂 → 再改数组。写了一组脚本自动化这个过程：`probe_ltp_common.sh` 批量跑全部 case，记录每个 case 的状态（通过/失败/超时/panic）、退出码、summary，输出 tsv。然后对照 tsv 决定哪些进 curated 列表。

脚本本身不值钱，但它改变了 case 筛选的工作方式——从"手动试"变成"机器扫一遍，人做决策"。

## 稳定性打磨

功能成型之后全部精力在稳定性上。目标是 `ltp_scoreable_cases.inc`（463 行）和 `ltp_scoreable_cases_rescan.inc`（372 行）里的 835 个 case 全部稳定通过。

### LTP 规模扩大和僵尸进程

随机 panic 在这个阶段集中出现——同一个 case 有时过有时不过。排查思路是：如果一个 case 单独跑能过、放回全集就炸，那问题大概率不在 case 本身，而是环境残留——上一轮的僵尸进程、未释放的文件描述符、脏的 buf cache。

僵尸进程是第一个被确认的问题。LTP 里 fork/wait 类 case 每轮产生大量子进程，如果父进程没及时 reap，僵尸把进程表占满，后续测试 fork 就失败了。加了每轮测试前的僵尸清理——遍历 `pool[]`，把 `state == ZOMBIE` 的全回收。同时把 `NPROC` 从 128 拉到 512。512 这个数字是基于 LTP 的 fork 类 case 最大并发数估算的——`fork14` 会同时存在 100+ 个子进程，加上系统守护进程和测试框架本身，128 确实太紧。

### 时钟中断精简

`timer_tick()` 原来是在硬中断里扫全进程表的。NPROC=512 的时候，每次时钟中断要遍历 512 个进程检查定时器——这太重了。而且万一中间被其他中断打断，处理时间过长，下一个 tick 的 `set_next_timeout()` 就设不上——`set_next_timeout()` 原来在 `timer_tick()` 末尾才调。

改了两点。一是 tick 路径只做 `ticks++` + `wakeup(&ticks)`，定时器到期扫描移到 `timer_active_list`（只有启用了 timer 的进程才挂）。二是 `set_next_timeout()` 移到 `devintr()` 入口——中断一进来就先重装下一次超时，不管后续处理花多长时间，下一个 tick 不会被漏掉。这个改动在 `hsai_trap.c` 里只加了三行，但效果很明显——系统不会再"时钟停住"。

### sleep/nanosleep 修正

`sys_nanosleep` 的 ABI 对不上。用户态声明是 `timeval_t`（微秒精度），内核按 `timespec_t`（纳秒精度）解析——参数位宽不同，导致传进来的时间值是歪的。体感上 sleep 时长经常不对，查了很久才发现是这个低级错误。统一改 `timespec_t`。

`sleep_on_chan()` 原来只设置 `p->state = SLEEPING`，线程的 `state` 还是 `t_RUNNABLE`。对于早期只有单线程的 busybox 测试不会出事，但 glibc LTP 的 pthread case 跑起来之后就不行了——`scheduler()` 选线程的时候看的是线程状态，如果一个线程 `state == t_RUNNABLE` 但进程 `state == SLEEPING`，调度器会尝试调度它，然后各种奇怪现象出来。改为睡眠/唤醒时进程和线程状态同步切换。四条唤醒路径（`wakeup`、`kill`、`kill_all`、`tgkill`）全改了。

`nanosleep` 还有一个被信号打断的问题。进程 `nanosleep` 期间收到 `SIGALRM`，应该醒来返回 `-EINTR` 并写回剩余时间。但原来的实现只检查了 `p->killed` 标志，pending signal 不检查。加上之后，LTP 里 alarm 相关的 case（`alarm03`、`setitimer01` 等）通过率明显上升。

### socket 泄露

跑久了发现 `socket()` 调多了返回 `-EMFILE`。追下去发现进程退出时 socket 类型 fd 的 `fileclose()` 路径里只关了 fd 本身，没有释放 socket 的内核对象（`sock` 结构体）。补上就行，改动在 `fileclose()` 和 `sys_close()`。

### 父子进程不同步——三轮修复

这个是最折腾的 bug。现象：子进程 `exit()` 了，父进程 `waitpid()` 等不到。或者父进程 `waitpid()` 返回了但子进程还没开始跑。表象是同步问题，但根因可能在好几层——进程创建的时序、调度器的选择策略、wait 路径的状态检查。

第一版思路是回退。把之前的很多改动撤了——`vfs_ext4` 里 41 行、`process.c` 里 32 行、`syscall.c` 里 74 行——回到一个已知比较稳定的版本，然后重新组织用户态测试流程。同时把 `NPROC` 拉到 512，去掉 `sleep 5` 等待（原来每轮测试之间睡 5 秒等系统稳定，改成靠同步机制保证）。

但回退之后问题还在，而且测例顺序一调就又出来。于是第二版换思路——加时钟标定。在用户态测试调度器里先跑一组对时间敏感的基准 case（比如几个简单的 fork/exit 循环），根据实际执行时间校准后续 case 的超时阈值。QEMU 里的时钟精度本来就不高（纯软件模拟定时器），不同硬件环境下 tick 速度差别很大。校准之后超时判断至少是相对合理的。

同时去掉 `busybox timeout` 包装。原本每个 LTP case 用 `busybox timeout 30s ./testcase` 防止卡死，但这层包装本身引入额外的 fork、信号处理和等待，反而加剧了同步问题。去掉之后让内核定时器直接兜底。

第三版彻底换了思路——不在内核修补，而是重写用户态测试调度器。原来的测试执行路径比较简单：`system("./testcase")` 或者 `busybox timeout`。改成显式的 fork/exec/wait 三阶段：先 `fork()`，子进程 `execve()` 测试 binary，父进程 `waitpid(pid, &status, WNOHANG)` 轮询，超时了 `kill(pid, SIGKILL)`。每个阶段的状态是显式管理的，出问题能准确知道卡在哪一步。两个 `user.c` 各重写了 282 行。

这个 bug 的教训是：并发同步问题不要在内核层盲目修补——先确认用户态的测试调度方式本身是不是引入了不确定因素。用 `system()` 和 `busybox timeout` 本质上都是把同步控制外包给了外部工具，但这些工具是为通用场景设计的，不一定适合高密度的测试调度。

## 一些体会

**干净镜像是前提。** 测试镜像跑着跑着就被写脏——inode 异常、目录损坏、free block 计数不一致。每次测试前"复制临时镜像 + e2fsck"应该是一个不可跳过的步骤。如果不这样做，花在排查"为什么这次跑不过"上的时间至少翻倍。

**回退是常态，不是失败。** 很多次"修了一个又坏另一个"之后，策略就变成了——先回到上一版能正常跑通的基线，再小步加改动。这不是保守，是效率。在一个不稳定的基线上继续改，排查成本是指数级的。

**随机 panic 背后基本都不是随机。** 每次追到最后，根因差不多都是底层状态被悄悄写坏——线程 kernel stack 越界、`kernel_sp` 指错位置、futex 队列里残留已释放线程的引用。只是触发爆炸的时机取决于调度顺序。这种问题优先从 `clone_thread`、kernel stack、调度切换、futex/signal 交汇这几个高嫌疑区域排查。

**自动化探测比手工试效率高一个数量级。** probe 脚本写起来半天，但之后每次扩大 LTP 规模能省下来的是数十次"改数组 → 编译 → QEMU 跑 → 崩溃 → 看日志"的循环。先让机器扫一遍，拿数据再决策。
