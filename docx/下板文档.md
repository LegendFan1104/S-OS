# 下板文档

> 记录 SuperOS 内核在 VisionFive 2（RV，JH7110）和 2K1000（LA）两块真实开发板上运行的完整过程、命令与踩坑记录。
> 本文档持续更新：每遇到一个新问题，按章节补充到对应平台下面。

---

## 1 整体思路与过程

### 1.1 总体流程

内核先在 QEMU 上开发调试，再构建成板载镜像，通过 U-Boot + TFTP 加载到真机运行，文件系统按平台分别放到 SD 卡（RV）或 SATA 盘（LA）：

1. QEMU 开发调试：`make all` + qemu 命令（内核逻辑与 QEMU 一致，板载跑的就是同一套逻辑）。
2. 板载构建：RV 用 `make clean && make board-rv-bin SDMMC_DRIVER=1`，LA 用 `make clean && make board-bin SATA_DRIVER=1`。
3. U-Boot 加载：通过串口进入 U-Boot，设置网络后用 `tftpboot` 把内核 bin 下载到板子内存，再 `go` 运行。
4. 文件系统：RV 把 `sdcard-rv.img` 用 balenaEtcher 烧进 microSD 卡；LA 把 `sdcard-la.img` 写入 SATA 盘。
5. 板载运行测试用例：内核启动后挂载文件系统，运行与 QEMU 中相同的测试逻辑。

### 1.2 硬件连接

| 平台 | 需要连接 |
| --- | --- |
| RV（VisionFive 2） | microSD 卡（≥16GB，建议 32GB）、网线、USB-TTL 串口线、Type-C 5V/3A 电源 |
| LA（2K1000） | SATA 盘、网线、USB-TTL 串口线、板载电源 |

串口接线（RV 40pin 排针）：Pin 8 = UART0 TX（接 USB-TTL 的 RX）、Pin 10 = UART0 RX（接 USB-TTL 的 TX）、Pin 6 = GND。TX/RX 必须交叉，GND 必须共地。

电脑侧：有线网卡设静态 IP `192.168.137.1` / 掩码 `255.255.255.0`（网关留空）。

### 1.3 软件准备

- PuTTY：Serial，115200、8N1、**流控全部关闭**（None）。
- tftpd64：目录指向 `D:\oskernel-board`，IP 选 `192.168.137.1`；防火墙放行 tftpd64（UDP 69）。
- balenaEtcher：烧 SD 卡 / SATA 盘镜像。
- 构建环境：WSL Ubuntu-22.04 + Docker（sos2026）容器；WSL 内也装好了 riscv64 / loongarch64 交叉工具链，可直接构建。

### 1.4 构建与产物

```bash
# QEMU（开发调试）
make all

# RV 板载
make clean && make board-rv-bin SDMMC_DRIVER=1

# LA 板载
make clean && make board-bin SATA_DRIVER=1
```

产物统一放到 `D:\oskernel-board`，按平台命名：

| 平台 | 产物 | U-Boot 加载地址 |
| --- | --- | --- |
| RV | `rv.bin` | `0x80200000` |
| LA | `la.bin` | `0x9000000090000000` |

### 1.5 进入 U-Boot 与网络配置

- 2K1000：上电/复位后看到 `Press c to enter u-boot console`，**按 c** 进入命令行。
- VisionFive 2：看到 `Hit any key to stop autoboot` 时**按任意键**进入命令行。

网络参数只需要设置一次并 `saveenv`，就会存入板载 SPI flash，之后断电重启都保留：

```text
setenv ipaddr 192.168.137.223
setenv serverip 192.168.137.1
saveenv
ping 192.168.137.1        # Host is alive 即网络通
```

注意观察 `saveenv` 是否打印 `Saving Environment to SPIFlash... done/OK`，没打印说明没存上。

### 1.6 加载内核并运行

RV：

```text
tftpboot 0x80200000 rv.bin
go 0x80200000
```

LA（地址必须是 64 位窗口地址，与 QEMU 内核加载地址一致）：

```text
tftpboot 0x9000000090000000 la.bin
scsi reset
go 0x9000000090000000
```

> 地址是两平台最容易混的点：`0x80200000` 是 VF2（OpenSBI 约定）专用；LA 用 `0x9000000090000000`，不能用裸物理地址 `0x90000000`（会报 reserved memory 错误）。

每次重启后内核需要重新 `tftpboot` + `go`（内核只活在内存里）；网络参数 `saveenv` 过就不用重设。

### 1.7 文件系统准备

RV（microSD / TF 卡）：

- 镜像：`sdcard-rv.img`（14GiB，前 512MB 是 ext4 文件系统，含全部测试用例，后面是空的）。
- 烧录：Windows 上 balenaEtcher 选镜像 → 选卡 → Flash（会清空整卡）。烧完 Windows 提示"需要格式化"直接取消。
- 卡要求：镜像正好 14GiB，16GB 卡可能卡边，建议 32GB。

LA（SATA 盘）：

- 镜像：`sdcard-la.img`（14GiB **裸 ext4**，没有分区表，从 LBA 0 开始写即可；内核 blockdev 的 `part_size` 硬编码 16GB）。
- 方式一（推荐，有转接器）：拆下 SATA 盘，USB-SATA 转接器接电脑，用 balenaEtcher 直接烧，和 SD 卡一样。
- 方式二（无转接器）：镜像分块后用 U-Boot 的 TFTP + `scsi write` 写入，见第三章"LA 坑"的 SATA 烧录小节。

### 1.8 上电自动启动

把加载命令写进 U-Boot 的 `bootcmd`，之后每次上电自动下载并运行内核：

RV：

```text
setenv bootcmd 'tftpboot 0x80200000 rv.bin; go 0x80200000'
setenv bootdelay 1
saveenv
```

LA：

```text
setenv bootcmd 'tftpboot 0x9000000090000000 la.bin; scsi reset; go 0x9000000090000000'
setenv bootdelay 1
saveenv
```

配合电脑侧把 tftpd64 放进开机启动（Win+R 输入 `shell:startup`）或装成服务，即可做到"板子上电就进系统"。TFTP 失败时 U-Boot 会掉到提示符等手动输入。

### 1.9 调试方法论

- 串口日志是主要依据：panic 会打印文件和行号（如 `panic:[sdmmc.c:xxx]`）。
- RISC-V trap 反汇编定位：日志给出 `sepc`，用 `riscv64-linux-gnu-objdump -d --start-address=...` 和 `addr2line -e <elf>` 定位到具体源码行。
- DW MMC 的错误用 `RINTSTS` 数值对照中断位表（bit2=命令完成、bit8=响应超时、bit10=主机数据饥饿、bit4/5=FIFO 收发请求等）。
- 驱动问题优先对照官方驱动源码（U-Boot `drivers/mmc/dw_mmc.c`、`include/dwmmc.h`，Linux `drivers/mmc/host/dw_mmc.c/.h`）逐行核对，不要凭记忆写寄存器位。

## 2 RV（VisionFive 2）遇到的坑

按调试顺序记录，每条含现象、原因、解决。

### 2.1 串口完全无输出

- **现象**：PuTTY 打开对应 COM 后屏幕空白。
- **原因排查顺序**：
  1. COM 口选错（每根 USB-TTL 线有独立 COM 号，设备管理器里拔插确认）。
  2. 接线错误：TX/RX 必须交叉（Pin8 接串口线 RX，Pin10 接串口线 TX），GND 必须共地。
  3. PuTTY 流控没关（硬件/软件流控开着会导致完全没反应）。
  4. 供电不足：必须用 Type-C 5V/3A 电源，不能用电脑 USB 口供电。
  5. 启动拨码：出厂默认 `00` = QSPI NOR（从板载 SPI flash 的 U-Boot 启动）；如果被拨到 `01`（SDIO 模式），板子会去找 SD 卡里的引导固件，而我们的镜像只有 ext4 文件系统、没有 SPL/U-Boot，会完全没输出。
  6. 板载 SPI 固件被清/损坏：拨到 `11`（UART 模式）按官方 QSG 4.4 走 UART 恢复流程重刷固件。

### 2.2 内核一启动就 kerneltrap：scause=0x5，stval=0x101004

- **现象**：`go 0x80200000` 后立刻 `unexpected interrupt scause=0x5`，`sepc=0x80218892`，`stval=0x101004`，panic `kerneltrap`。
- **原因**：内核 `timer_init()` 会读 QEMU virt 特有的 **Goldfish RTC**（0x101000/0x101004）来校准时钟，真机 JH7110 上这个地址没有设备，一读就是 load access fault（scause=0x5）。
- **解决**：新增 `BOARD_JH7110` 宏（板载构建自动定义）：`read_rtc_seconds()` 直接返回固定基准时间，`calibrate_timer_freq_from_rtc()` 不再做 RTC 差分测频，改用 JH7110 CLINT 的真实频率 **4MHz**（依据内核 `jh7110-common.dtsi` 的 `timebase-frequency = <4000000>`）。
- **教训**：QEMU 专属外设（Goldfish RTC 等）在真机上不存在，板载构建要用宏隔离。

### 2.3 sdmmc CMD0 timeout（RINTSTS=0x0）

- **现象**：`[sdmmc] init JH7110 SD/MMC @0x16020000` 后 `CMD0 timeout (RINTSTS=0x0)`。
- **原因**：JH7110 的 SDIO1 外设上电后**时钟默认关闭且处于复位态**（SPI NOR 启动时 U-Boot 不初始化 SDIO）。只写 DW MMC 寄存器没用，命令根本发不出去。
- **解决**（参照 Linux/U-Boot 时钟驱动）：
  - SYS_CRG（0x13020000）里时钟寄存器偏移 = 时钟 ID × 4：SDIO1_AHB=92 → 0x170 bit31 使能；SDIO1_SDCARD=94 → 0x178 bit31 使能 + bits[3:0] 分频（写 8，CIU ≈ 50MHz）；复位 SDIO1(id=65) → 0x300 bit1，写 0 释放。
  - **同时必须在 vmem 页表里映射 SYS_CRG**（0x13020000），否则 MMU 开启时访问会 page fault。

### 2.4 CMD55 响应超时（RINTSTS=0x100）

- **现象**：CMD0/CMD8 都过了，CMD55 报 RTO（0x100）。
- **原因**：DW MMC 的命令号字段是 **6 位**（0-63），驱动用 `& 0x1F` 把 CMD55（0x37）截断成了 CMD23，卡在 IDLE 态收到 CMD23 不响应。
- **解决**：命令号掩码改为 `& 0x3F`。U-Boot 是直接把完整命令号写进 CMD 寄存器（`cmdr = cmd->opcode`）。

### 2.5 ACMD41 响应错误（RINTSTS=0x42）

- **现象**：CMD55 正常，ACMD41 报 0x42（bit1 RE + bit6 RCRC）。
- **原因**：ACMD41 的响应是 **R3（OCR），没有 CRC 字段**，主机不能要求校验 CRC，驱动却带了 `RESP_CRC` 位。
- **解决**：ACMD41 只带 `RESP_EXP`，去掉 CRC 校验。U-Boot 里对应 `resp_type = MMC_RSP_R3`（无 CRC）。

### 2.6 读数据失败：read short (got 0/128)

- **现象**：卡初始化成功（SDHC/SDXC, ~30240 MB, RCA=0x1），但第一个 CMD17 读数据 FIFO 里一个字都没有。
- **原因**：DW MMC 的 **RW 位（bit10）语义是 0=读、1=写**，驱动写反了——读命令置了 RW 位，控制器把 CMD17 当"写数据"处理，等着往外发数据，所以 FIFO 永远空。
- **解决**：读命令（CMD17）不置 RW，写命令（CMD24）置 RW。U-Boot：`if (data->flags & MMC_DATA_WRITE) mode |= DWMCI_CMD_RW;`。

### 2.7 写数据失败：write CMD24 error（RINTSTS=0x410）

- **现象**：读正常，第一个写报 0x410 = HTO（bit10，主机数据饥饿超时）+ TXDR（bit4）。
- **原因**：两个问题叠加：① 数据命令漏了 `PRV_DAT_WAIT`（bit13），命令可能在数据线忙时发出；② 写命令发出后没有及时往 FIFO 喂数据，控制器等数据超时中止。
- **解决**：
  - CMD17/CMD24 都加上 `DW_CMD_PRV_DAT_WAIT`（U-Boot 对所有非 STOP 命令都加）。
  - 写路径：命令发出前**预填 FIFO**，命令等待期间 TXDR 一置位就继续补数据。
  - 命令等待循环只认响应错误（RE/RTO/RCRC），数据阶段错误（含 HTO）在数据循环里判定，与 U-Boot 的 DATA_ERR/DATA_TOUT 语义一致。

### 2.8 RV 其他注意事项

- SD 卡是 **microSD（TF）卡**，镜像 14GiB，用 ≥16GB 卡（建议 32GB）。
- 每次重启要重新 `tftpboot` + `go`；网络参数 `saveenv` 一次即可。
- 与 QEMU 的差异点都会在板载构建宏里隔离：`SDMMC_DRIVER=1`（磁盘走 SD/MMC 而非 virtio）、`BOARD_JH7110=1`（RTC/时钟走真机配置）。
- 已知待优化：当前 1 位总线 + FIFO-PIO，后续可切 4 位总线（需发 ACMD6）和 IDMAC DMA 提速。

## 3 LA（2K1000）遇到的坑

> LA 目前已完成 U-Boot 加载流程和文件系统烧录方案，内核板载调试仍在进行中，本节会持续补充。

### 3.1 U-Boot 进入方式

- 2K1000 显示的是 **"Press c to enter u-boot console, m to enter boot menu"**——进入命令行的按键是 **c**，不是空格或回车。

### 3.2 tftpboot 报 "trying to overwrite reserved memory"

- **现象**：`tftpboot 0x90000000 kernel-la-board.bin` 报 `TFTP error: trying to overwrite reserved memory`。
- **原因**：`0x90000000` 是裸物理地址，落在 U-Boot 自己/保留内存区域；而内核链接在 64 位窗口地址 `0x9000000090000000`。
- **解决**：加载地址必须用完整的 **64 位窗口地址** `0x9000000090000000`（与 QEMU 里内核的加载地址一致），`go` 也用同一个地址。上板文档（rustoswhu）第 11 步明确要求"tftpboot 的地址和 QEMU 的加载地址一致"。

### 3.3 串口 MMIO 必须走 DMW0

- 参考他人文档（rustoswhu 上板.md）的坑：初始化了 DMW0（0x8000...）和 DMW1（0x9000...）后，**访问 MMIO 必须走 DMW0**（uncached），例如 UART `0x1fe20000` 要写成 `0x800000001fe20000`；在 QEMU 上走 DMW1 没问题，真机上不行。
- 我们板载构建的 `uart.c` 已按真机地址处理。

### 3.4 非对齐访问

- 2K1000 只支持**地址对齐**的数据访问，不支持的指令会在启动时一直报 `AddressNotAligned`。
- 编译必须启用对齐选项：Rust 内核用 `-Ctarget-feature=-ual`；我们的 C 内核板载构建已启用 `-mstrict-align`。

### 3.5 页表要求

- 2K1000 对页表检查比 QEMU 严格：用户地址的页表项要设置 V、P 和 MAT_NOCACHE 位（对应 RISC-V 的 UDA 三位）。页表不对时取指报 `instruction not exist`（实质是取指 page fault）。
- 我们的页表代码已按该要求处理。

### 3.6 SATA 镜像烧录

- 镜像 `sdcard-la.img` 正好 14GiB，是**裸 ext4**（无分区表），从 LBA 0 开始写；内核 `blockdev.c` 的 `part_size` 硬编码为 16GB，所以磁盘 ≥16GiB。
- **方式一（推荐）**：拆下 SATA 盘，USB-SATA 转接器 + balenaEtcher 直烧，和烧 SD 卡一样。
- **方式二（无转接器）**：TFTP 分块 + `scsi write`：
  1. WSL 里分块并生成命令脚本：
     ```bash
     cd /home/oskernel2026-sos
     mkdir -p la-flash/chunks
     split -b 16M -d -a 3 sdcard-la.img la-flash/chunks/chunk-
     python3 - <<'EOF'
     import os
     size = os.path.getsize("sdcard-la.img")
     chunk = 16 * 1024 * 1024
     sect = chunk // 512
     with open("la-flash/flash.cmd", "w") as f:
         f.write("scsi reset\nscsi info\n")
         for i in range(0, size, chunk):
             name = f"chunk-{i // chunk:03d}.bin"
             blk = i // 512
             f.write(f"tftpboot 0x9000000008000000 {name}\n")
             f.write(f"scsi write 0x9000000008000000 {blk} {sect}\n")
     EOF
     ```
  2. 把 `la-flash` 放到 tftpd64 目录，U-Boot 里 `scsi reset; scsi info` 确认盘。
  3. 有 mkimage 时打包成脚本一次跑完（`mkimage -A loongarch -T script ...` + `tftpboot` + `source`）；否则把 `flash.cmd` 分段粘贴到 PuTTY。
  4. 烧完验证：`tftpboot 0x9000000090000000 la.bin; scsi reset; go 0x9000000090000000`，文件系统能挂载即成功。

### 3.7 LA 其他注意事项

- 每次重启要重新 `tftpboot` + `go`；网络参数 `saveenv` 一次即可。
- `bootcmd` 自动化见第一章 1.8 节。
- 构建时 `SATA_DRIVER=1` 走板载 SATA（AHCI，vendor 0x0014 / device 0x7a08，PCI ECAM 0x1a000000，IRQ 19）；不定义则走 QEMU virtio。

### 3.8 SATA IDENTIFY 超时：DMA 结构不能放在 bank1 高地址

- **现象**：内核启动到 `[sata] HBA at 0x400e0000`、`[sata] port 0 spinup took 0 ms` 后打印
  `[sata] io timeout: cmd=0xec (CI=0x1 TFD=0x58)`，之后用户态创建完成但再无输出（IDATA 命令发不出去，磁盘读写全部卡死）。
- **原因**：2K1000LA 的 SATA DMA（AHCI 控制器做主设备访问内存）**无法访问 bank1 高物理地址**
  （bdinfo 里 `memory[1]` 起点 `0x9000000090000000`，物理 2.25GB+）。内核所有静态缓冲都在
  链接地址 `0x9000000090...`（bank1），把端口寄存器的 CLB（命令列表）/FB（FIS 接收区）填成这些
  高地址后，控制器取不到命令，端口一直忙（TFD BSY/DRQ 置位），命令永不完成。
  参考帖子：bbs.elecfans.com/jishu_2448264_1_1.html（同样现象：CLB/FB 填高地址 → 命令发不出；
  换成 bank0 低地址 → 正常）。根因是 SoC 内部 IO 互连网络的地址窗口未配置/路由异常。
- **解决**：把 SATA 全部 DMA 结构固定在 **bank0 低地址**（物理 0~256MB）。内核里选物理
  `0x08000000`（128MB）：
  - U-Boot 的 reserved 区在 `0x0CBF4C90` 之后，不冲突；
  - 内核伙伴系统从 `KERNEL_DATA`（bank1）才开始管理，不会分配到这里；
  - 布局：cmdlist @ `0x08000000`（1KB）、fis @ `0x08000800`、cmdtbl @ `0x08000900`、
    dma @ `0x08000A00`（4KB bounce buffer）、ident @ `0x08001A00`。
  驱动里这 5 个缓冲从"静态数组"改成"指向固定物理地址的指针"，CPU 侧通过 DMW1 非缓存别名
  `0x8000...` 访问，`PA2VA()` 拿到的就是低物理地址；`sata_port_start` 的 memset 改用显式长度。
  AHCI 寄存器访问仍走原来的 `0x8000...` 窗口不变。
- **验证**：新镜像 `D:\oskernel-board\la.bin`（SHA256 `ffebced5...`），预期启动后看到
  `[sata] disk identified: 62533296 sectors (30533 MB)`，随后文件系统挂载、`run_submit` 跑测试。
- **教训**：QEMU 里 DMA 用哪段物理内存都行，真机 SoC 的 DMA 地址窗口有实际限制；带 DMA 的
  控制器驱动，共享缓冲必须放到外设可达的物理区域（通常用低地址 bounce buffer）。
